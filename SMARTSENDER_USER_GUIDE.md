# SmartSender AI — Complete User and Operations Guide

## 1. What SmartSender AI is

SmartSender AI is a workspace-based email creation and sending application. It combines contact management, AI-assisted writing, email preflight checks, reusable sending-provider connections, campaign previews, and controlled delivery in one local dashboard.

The application is designed around a review-first workflow:

1. Connect a private workspace.
2. Configure an approved email provider.
3. Add authorized contacts.
4. Generate or write an email draft.
5. Review the personalized preview and preflight score.
6. Explicitly confirm the send.
7. Check the provider's delivery events for the final outcome.

Creating a draft, adding contacts, importing a CSV, or opening a preview never sends an email. A campaign is sent only after the user presses the final send button and accepts the confirmation prompt.

SmartSender AI must be used only for recipients who have consented to receive marketing messages or who are authorized by an existing transaction, account, or contract. It is not intended for purchased lists, scraped addresses, unsolicited bulk email, or attempts to bypass provider policies.

## 2. Main components

SmartSender AI consists of:

- **Dashboard:** The browser interface at `http://127.0.0.1:8000`.
- **FastAPI application:** Handles workspace access, contacts, drafts, previews, verification, provider connections, and sending.
- **OpenAI integration:** Produces email and signature drafts from a user-supplied brief.
- **Email providers:** Delivers approved messages through SMTP, Microsoft 365 SMTP, Microsoft Graph, or SendGrid.
- **SQLite workspace database:** Stores local workspace records, contacts, campaigns, hashed workspace keys, and encrypted provider credentials.
- **Redis queue:** Stores queued transactional jobs.
- **Transactional worker:** Processes queued transactional email batches in the background.

The dashboard does not require Node.js. Its frontend uses browser-native HTML, CSS, and JavaScript, while the server runs on Python.

## 3. Starting SmartSender AI locally

### Required software

- Python and the project's `.venv`
- Docker Desktop
- WSL 2 and hardware virtualization
- Redis, supplied by the project's Docker Compose configuration

### Start Redis

Open PowerShell in the SmartSender project folder:

```powershell
docker compose up -d
docker compose ps
```

The expected container is `smartmailer-redis`, normally exposed locally on port `6379`.

### Start the dashboard and API

In PowerShell:

```powershell
.\.venv\Scripts\uvicorn.exe app:app --reload
```

Keep the window open. Visit:

```text
http://127.0.0.1:8000
```

The developer API remains available at:

```text
http://127.0.0.1:8000/docs
```

The health check is:

```text
http://127.0.0.1:8000/health
```

### Start the background worker

Open a second PowerShell window in the project folder:

```powershell
.\.venv\Scripts\python.exe transactional_worker.py
```

The worker is required only for jobs submitted to the transactional queue. Normal dashboard campaign sends are performed synchronously and do not use this worker.

## 4. First-time setup

### Option A: Connect an existing workspace

1. Open **Settings**.
2. Find **Workspace access**.
3. Paste the workspace API key previously generated by SmartSender.
4. Select **Connect existing workspace**.

The key is kept in the browser session. Closing the browser session may require it to be entered again.

### Option B: Create a workspace

1. Open **Settings**.
2. Enter a business or workspace name.
3. Enter a key label such as `production`, `office-laptop`, or `owner`.
4. Select **Create workspace**.
5. Copy the generated workspace API key immediately.
6. Store it in a password manager or another secure secret store.
7. Confirm that the key has been saved.

The key label is only a description. Never enter an email password, OpenAI key, SendGrid key, or Microsoft secret into the label field.

Every request to **Create workspace** creates a different workspace with a different API key. Do not repeatedly create workspaces when the intention is to reconnect to an existing one.

## 5. Understanding the different keys

SmartSender AI can use several unrelated secrets:

- **Workspace API key:** Generated by SmartSender. It authorizes access to one workspace.
- **OpenAI API key:** Obtained from OpenAI. It authorizes AI draft generation.
- **SendGrid API key:** Obtained from SendGrid. It authorizes SendGrid email delivery.
- **Microsoft Graph client secret:** Obtained from Microsoft Entra. It authorizes Graph delivery.
- **SMTP or app password:** Obtained from the mailbox or email-hosting provider. It authorizes SMTP delivery.
- **Credential encryption key:** A Fernet key stored in the server environment. It encrypts provider credentials before database storage.

These values are not interchangeable. Never share them in messages, screenshots, source control, or public documentation.

## 6. Configuring an email provider

Open **Settings → Email provider**. Choose a connection name, select the provider, fill in its required fields, and select **Save encrypted connection**.

A connection name is a reusable internal label such as:

```text
primary-email
```

Campaigns refer to this name rather than containing provider secrets.

### SendGrid

Required values:

- SendGrid API key
- Verified sender name
- Verified sender email

The sender address or domain must be authenticated according to the SendGrid account's requirements.

### General SMTP

Required values:

- SMTP hostname
- Port, commonly `587`
- SMTP username
- SMTP password or app password
- Sender name
- Sender email

SmartSender uses STARTTLS for its general SMTP connection. The password must be the SMTP or app password required by the provider—not the Windows PIN, SmartSender workspace key, or ordinary password when the provider specifically requires an app password.

### Microsoft 365 SMTP

Required values:

- Microsoft 365 email/username
- App password or permitted SMTP credential
- Sender name
- Sender email

The Microsoft tenant must permit the selected SMTP authentication method. Some organizations disable SMTP AUTH and require Microsoft Graph instead.

### Microsoft Graph

Required values:

- Tenant ID
- Client ID
- Client secret
- Sender email

The Entra application must have the required Microsoft Graph mail permission and administrator consent.

### What “saved” means

The application checks that all required fields exist, then encrypts the credentials before storing them. A successful save does not guarantee that the provider will accept the credentials. Authentication and sender authorization are ultimately tested when the provider is contacted.

## 7. Overview dashboard

The **Overview** page shows:

- Number of campaigns in the connected workspace
- Number of saved contacts
- Number of configured provider connections
- AI readiness
- Recent campaign drafts
- A quick-start sequence

A dash (`—`) means no workspace is connected. Zero means a workspace is connected but currently has no records of that type.

## 8. Contacts and lead verification

### Add one contact

1. Open **Contacts**.
2. Enter the email address.
3. Optionally enter the first name and company.
4. Select **Add contact**.

### Import contacts from CSV

1. Prepare a UTF-8 CSV file with an `email` column.
2. Optional columns can include `first_name`, `company`, or other personalization values.
3. Open **Contacts**.
4. Select the CSV import area and choose the file.
5. Review the number saved and any skipped rows.

The maximum CSV size is 5 MB. Importing contacts does not create or send a campaign.

Example:

```csv
email,first_name,company
ada@example.com,Ada,Example Company
grace@example.org,Grace,Example Organization
```

### What contact verification checks

Before a contact is accepted, SmartSender checks:

- Whether the address has a valid-looking email format
- Whether the receiving domain publishes an MX mail record
- Whether the address is duplicated in the submitted list

### What contact verification does not guarantee

SmartSender does not probe the individual mailbox. Many receiving servers block or conceal mailbox-level checks. Therefore:

- A valid format does not prove the person exists.
- An MX record proves only that the domain is configured to receive mail.
- An accepted contact can still bounce.
- A provider can still reject, suppress, or defer delivery.

The current dashboard accepts or rejects contacts; it does not display a numeric lead-verification score. For mailbox-level scoring, a dedicated verification provider would need to be integrated.

## 9. AI Composer

The **AI Composer** turns a campaign brief into an editable, reviewable campaign draft.

### Fields

- **Campaign name:** An internal title used to identify the draft.
- **Email type:** `Marketing` or `Transactional`.
- **Sending connection:** The provider connection that will be used if the campaign is later sent.
- **Purpose:** What the message should accomplish.
- **Audience:** Who will receive it.
- **Brand voice:** Tone and writing style.
- **Call to action:** The next step requested from the recipient.
- **Personalization variables:** Comma-separated fields such as `first_name` and `company`.
- **Recipients:** Saved contacts selected for this particular draft.

### Generate a draft

1. Complete the brief.
2. Select at least one authorized recipient.
3. Select **Generate draft**.
4. Wait for the AI response.
5. Review the subject, body, and deliverability report.

Generation creates a campaign with `draft` status. It does not send email.

AI output can contain errors, incorrect claims, unsuitable promises, or formatting problems. A person must review it before delivery.

## 10. Personalization

Campaign templates can use saved contact values. Common values include:

```text
first_name
company
email
```

If `first_name` is missing, SmartSender makes a local best-effort guess from the part of the email address before `@`. Role-based addresses such as `billing@example.com` use a neutral greeting.

Personalization is rendered separately for each recipient during preview and sending.

## 11. Email-body preflight and deliverability score

SmartSender analyzes generated and previewed email content before sending.

The report checks signals including:

- Risky or spam-like phrases
- Subject-line length
- Excessive capitalization
- Multiple exclamation marks
- Number of external links
- Insecure `http://` links
- Missing unsubscribe language in marketing email
- Basic HTML structure

The result includes:

- Risk score from `0` to `100`
- Risk level: `low`, `medium`, or `high`
- Detected issues
- Recommendations
- External-link count

A lower score represents fewer detected risk signals. This is a heuristic content preflight, not a provider certification and not an inbox-placement guarantee.

The score does not independently verify:

- SPF, DKIM, or DMARC configuration
- Domain or IP reputation
- Provider rate limits
- Spam complaints
- Bounce history
- Whether a specific mailbox exists
- Whether a receiving provider will place the message in Inbox, Promotions, Junk, or reject it

## 12. Campaigns

The **Campaigns** page lists saved campaign records, including:

- Campaign name
- Subject
- Draft or send status
- Preview action
- Delete action for unsent drafts

### Preview a campaign

1. Open **Campaigns**.
2. Select **Preview**.
3. Review the rendered subject and email body.
4. Check which recipient is being used for the preview.
5. Review the deliverability risk score.

Previewing does not send email.

### Send a campaign

1. Preview the campaign.
2. Confirm that the content, provider, recipients, links, personalization, consent, and legal requirements are correct.
3. Select **Review complete — send campaign**.
4. Accept the final browser confirmation.

SmartSender then renders and submits a separate message for each campaign contact.

The final report shows how many messages were accepted or failed. “Accepted” means the configured provider accepted the submission; it does not prove inbox delivery.

### Delete a campaign

Only drafts can be deleted. A campaign that has already been processed remains in the workspace history.

## 13. Transactional email functions

Advanced transactional operations are available through the developer API at `/docs`.

### Single transactional send

`POST /v1/transactional/send` sends one approved message using a named workspace provider connection.

It supports:

- Recipient address
- Subject
- HTML or text content
- Bundled template name
- Template variables
- Optional signature
- Attachments

### Small transactional batch

`POST /v1/transactional/send-batch` sends one contract-related notification to no more than 25 authorized recipients.

### Queued transactional job

`POST /v1/transactional/queue` queues a larger transactional operation. It requires:

```json
{
  "confirm_transactional": true
}
```

The default configuration:

- Accepts up to 10,000 recipients per queued job
- Processes batches of 50
- Waits five minutes between batches

These limits can be configured through environment variables.

### Queue status

`GET /v1/transactional/queue/{job_id}` returns progress without exposing recipient addresses or provider credentials.

The queue requires Redis and the running `transactional_worker.py` process.

## 14. Signatures

SmartSender does not automatically add a signature to manually created transactional messages.

Available options include:

- Supply `signature_html` on an individual request.
- Use the bundled `default` signature by name.
- Generate signature options through `POST /v1/ai/generate-signature`.
- Save a selected workspace signature through `PUT /v1/workspace/signature`.

A saved workspace signature is appended to future AI-generated drafts. It does not silently modify manual transactional requests.

## 15. Workspace keys and multiple users

Each person or integration should receive a separate workspace key instead of sharing the owner's key.

Advanced key operations:

- `POST /v1/api-keys`: Create a separate key for another approved device or integration.
- `GET /v1/api-keys`: List safe key records without displaying secret values.
- `DELETE /v1/api-keys/{key_id}`: Revoke one lost or unused key.
- `POST /v1/api-keys/rotate`: Replace the current key and immediately revoke the old one.

Full keys are shown only at creation or rotation time. Losing an unrecorded key requires creation of a replacement.

## 17. Windows Firewall

For local development:

- Allow Docker Desktop on **Private networks** when required.
- Leave **Public networks** unchecked.
- Do not expose Redis port `6379` to public networks.
- Do not publish the development server directly to the internet.

The local address `127.0.0.1` is accessible only from the same computer.

## 18. Publishing to the web

The local application should not be exposed directly by opening router or firewall ports.

A production deployment should provide:

- HTTPS
- Proper user accounts and login sessions
- Separate access for each person
- Managed secrets
- Persistent database storage
- Private Redis
- Background worker
- Rate limiting and abuse controls
- Backups
- Monitoring and provider-event handling
- A domain with authenticated SPF, DKIM, and DMARC records

After deployment, users receive the HTTPS application URL and their own access credentials. They must never receive the server `.env`, encryption key, provider password, database, Redis password, or owner's workspace key.

## 19. Troubleshooting

### Dashboard does not open

Confirm the Uvicorn window is running:

```powershell
.\.venv\Scripts\uvicorn.exe app:app --reload
```

Then open `http://127.0.0.1:8000/health`. A healthy response contains:

```json
{"status":"ok","service":"SmartMailer AI"}
```

### Docker or Redis does not run

Check:

```powershell
wsl --status
wsl --list --verbose
docker version
docker compose ps
```

WSL should use version 2, the Docker client should show a server section, and `smartmailer-redis` should show `Up`.

### Workspace key is rejected

Possible reasons:

- An OpenAI or provider key was entered instead of the SmartSender workspace key.
- The key belongs to a different workspace.
- The key was rotated or revoked.
- A new tenant was created accidentally and its new key was confused with the old one.
- The key was copied with missing or extra characters.

### Email provider says invalid password

Confirm that:

- The selected provider is correct.
- SMTP uses the provider's SMTP or app password.
- Microsoft 365 permits the chosen authentication method.
- SendGrid uses an API key rather than the account password.
- The sender address is verified and authorized.
- No leading or trailing spaces were copied.

### Contact is rejected

Check the address format and confirm that the receiving domain has a valid MX record. A temporary DNS lookup failure can also cause domain verification to fail.

### AI generation fails

Check:

- `OPENAI_API_KEY` is configured.
- The API account has access and available usage.
- The computer or server can reach the OpenAI API.
- The purpose, audience, and call to action meet the minimum field lengths.

### Campaign was accepted but not received

Provider acceptance is not inbox delivery. Check:

- Provider activity/events
- Bounce or suppression lists
- Spam or junk folder
- Sender-domain authentication
- Recipient consent and engagement
- DMARC alignment
- Provider quotas and rate limits

## 20. Recommended daily operating procedure

1. Start Docker, SmartSender, and the queue worker if queued jobs are needed.
2. Connect the correct workspace.
3. Confirm the expected provider connection is shown.
4. Add or import only authorized contacts.
5. Create an AI draft.
6. Manually review every factual statement and link.
7. Review the lead-validation result during contact acceptance.
8. Preview the personalized message.
9. Review the deliverability score and correct avoidable warnings.
10. Confirm the selected recipients and sender identity.
11. Send a small internal test where appropriate.
12. Confirm the production send.
13. Monitor provider events, bounces, complaints, and unsubscribes.
14. Remove suppressed recipients from future campaigns.

## 21. Important limitations

- Lead validation checks format and the receiving domain, not individual mailbox existence.
- Deliverability scoring is heuristic and cannot guarantee inbox placement.
- AI output requires human review.
- Provider acceptance is not proof of delivery.
- The current dashboard is suitable for local operation; public multi-user deployment requires additional production security and storage work.
- Campaign sending is synchronous and currently limited to 100 normalized unique contacts per draft.
- Queued transactional jobs are for authorized transactional recipients, not cold marketing.
